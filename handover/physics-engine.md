Read brain.md first.

Project: hunter2 (this repo). A browser game in C, compiled to wasm, rendered with WebGPU through our own thin JS bridge. Engine written from scratch. The game may end up 2D or 3D, not decided yet.

The main goal is learning: we work through Ian Millington's "Game Physics Engine Development" chapter by chapter and build its physics engine together in src/phys/. The physics comes first, the game second. Second goal: everything lightning quick, which is why we stay with C + wasm + our own WebGPU bridge. Rendering, camera and tooling only exist to see and check the physics: keep them cheap, do not let them grow into their own project.

Setup: run ./setup.sh first. It checks the tools (it test builds a tiny wasm), clones the book's source code, extracts the book text and sets the git identity, and only does what is missing. Tools come from PATH, except clang falls back to Homebrew's LLVM when the clang on PATH cannot build wasm32 (find_clang.sh; override with CLANG, WASM_LD). If it reports MISSING, fix what you can (tools: ask before installing) and ask me for the rest. The book PDF is copyrighted and cannot be downloaded: I copy it into the repo root myself (any "Game Physics Engine Development*.pdf").

Then read:
- focus/physics-engine.md: this task. Goal, book map, physics state, decisions, machine notes, open questions, log.
- focus/architecture.md, the Decisions section: code rules (layers, naming, unity build). They apply to all code.
- src/phys/, src/base/math.c, src/demo/ and src/game/game.c: the physics code and how demos plug in.

How we work: you read the book for me and explain what matters, short or in depth when I ask. We work in small steps in book order. Write code only when I direct it, small first. I review the code and tell you my preferences. Keep focus/physics-engine.md up to date yourself. Ask before changing brain.md. Measure before guessing, and when something regressed after a known change, bisect it: build variants that undo one piece at a time and let me compare them in the browser side by side (node serve.js <port> from a scratch copy). Headless node can miss what Chrome does: last session a 50x slowdown only showed in Chrome.

The book: reference/millington.txt (pages split by form feed), reference/chapters.txt maps chapters to pages (book page = pdf page - 23). Equations and figures do not survive as text, so read those pages from the PDF directly. Explain in your own words, no long excerpts. The book's own C++ source is in reference/cyclone-physics. All of these are gitignored, ./setup.sh makes them.

Checks: ./build.sh builds the game, ./test.sh runs the unit tests headless. tests/headless/*.mjs run the real game with a fake WebGPU (FRAMES=60 node tests/headless/sim.mjs for a short run, SCENE=<id> picks a demo, keys.mjs for input and camera, jitter.mjs for pile movement). The fake does not compile WGSL and its clock moves exactly one step per frame, so shader changes and frame timing are only really checked in the browser. Run them after changes. Only tell me about them when it matters. I check every change in Chrome, on Windows (144 Hz monitor) or an M4 MacBook Air (npm start: runs ./build.sh, then node serve.js on http://localhost:8000).

Where we are (2026-10-31): physics covers book ch 2-4 (particles, semi-implicit Euler, damping) plus our own box walls and sphere collisions, and now the ch 5 code. Demos: one file per demo in src/demo/, a demo bar of HTML tabs along the bottom, [ and ] to switch, ?scene=<id> in the URL. The only demo so far is "balls" (Erasmos Balls, ch 3). Demos are dispatched by switch with FORCE_INLINE on step and draw: as separate functions Chrome ran them so slowly that 2000 balls fell to 1-3 fps (unresolved curiosity, pinned in the focus file's open questions). Still open: I want a clangd LSP plugin; offer a compile_flags.txt with the wasm32 flags.

Ch 5 this session (src/phys/force.c, declared in phys/phys.h, unit tested): force generators as a kind enum + switch (ForceGen with FORCE_GRAVITY and FORCE_DRAG, force_update), not function pointers, so the force math inlines like the demos. Drag is written as -v * (k1 + k2 |v|), the book's formula without the normalize, so zero velocity gives zero force. ForceRegistry {regs, count, cap} works over an array the caller owns (no malloc, sized per demo); remove swaps the last pair in (order does not matter, forces add up). Built-in acceleration and damping stay, like book 5.3. Nothing uses the generators yet.
