# focus: physics-engine

Goal: learn how to write a physics engine by working through Millington's "Game Physics Engine Development" chapter by chapter, building it together in src/phys/. Learning the physics comes first, the game second. Rendering, cameras and tooling are only there to see and check the physics: keep them as cheap as possible (2026-10-31). Second goal: everything lightning quick. So we keep C + wasm + our own WebGPU bridge (raylib and three.js weighed and dropped 2026-10-31: both slower for many instances, raylib web is WebGL and DrawSphere builds vertices on the CPU every call). Render kit for the whole book, built once and kept minimal: instanced meshes (sphere, box), lines, a free camera.

## How we work here
- The user reads the book. Claude reads along: explains sections short or in depth, as asked.

- Explain the book in our own words. Short quotes are fine, no long excerpts.

- The engine is built in 3D, like the book, and stays generic. The game may end up 2D or 3D (not decided). If it goes 2D, we adapt then.

## Decisions
- Springs: one ForceGen kind per variant, like the book (user, 2026-10-31, over one kind with flags or a two-ended Spring outside the registry). Shared helper force_hooke. No abs on (length - rest): the book's ParticleSpring (and cyclone pfgen.cpp:83) has it, so a compressed spring pulls too. Same spot returns early (no NaN).
- Ch 6 demo: rope bridge (user, 2026-10-31). Sliders act live with no reset. Tried: damping and cable kind resetting the bridge, a reset starting the deck 1 m up (so spring vs bungee differ), drop kg live on all drops. User: it was fine before, reverted (2026-10-31). Known: at rest damping, drop kg and the cable kind show nothing (a stretched bungee is a spring).
- V2 replaced by V3 everywhere. Game uses z = 0 while it is flat (2026-10-13).
- Vector products return a value, no cphiz get_ pairs (2026-10-13).
- 3D ball scene done (2026-10-31). Demo system built, then on to ch 5 (user, 2026-10-31).
- Force generators: kind enum + switch (ForceGen, force_update), not function pointers, so the force math inlines (user, 2026-10-31). Registry storage passed in by the caller (sized per demo, no malloc). Remove swaps the last entry in (order does not matter, forces just add up). Prefix force_.
- Demos: no function pointers, switches plus FORCE_INLINE on hot step and draw (Chrome slowdown, see Open questions) (2026-10-31).
- Ch 5 demo: a cloud of bodies pulling on each other (book 3.2, eq 3.3: f = G m1 m2 / r^2), with sphere collisions. Random size, mass grows with size, so big ones pull harder (user, 2026-10-31). Generator FORCE_ATTRACT {other, g}: pull toward one body, one per body, registered on every other body (n(n-1) pairs, each pair computed twice). Same shape as the book's springs (ch 6, a generator holding the other end). No softening: collisions keep centers at least the radii apart.
- Explode is a force, not a start velocity (user, 2026-10-31): FORCE_EXPLODE {center, force}, the same force on every mass, so dv = F t / m and light bodies fly much faster (option A). Option B, force by area (r^2, dv ~ 1/r), needs the radius, which particles do not have. User found A too strong on the small ones (2026-10-31), so the cloud now does B in the demo: one generator per body with force k r^2, the engine unchanged. Later maybe the book's full explosion (ch 17.2.3, pdf 434: implosion, concussion wave, convection chimney, spin needs rigid bodies).
- Headless test over all demos (step 4) deferred until the second demo exists: sim.mjs covers balls, SCENE=<id> works in fake.mjs. Each demo will need its own "broken" checks (2026-10-31).
- 3D physics, like the book (2026-10-13). Game dimension not decided.
- phys/ depends on base only. Never render or platform.
- Damping is per step (no libc pow). Fine because the step is fixed.
- Collisions are contacts in a fixed step order (user, 2026-10-31, replaces push apart in particle_collide_spheres and particle_collide_box, both removed): forces, integrate velocity, find contacts, warm start, solve, integrate position, bounce. The book's order (integrate, then resolve, push positions apart) adds angular momentum: a push is not an impulse. Contacts only use impulses along the line of centers, so momentum and L stay exact. Speculative (a pair may close its gap this step, not more), accumulated impulse >= 0 per contact, warm started (without it 4 passes let piles and the cloud sink). Leftover overlap past PHYS_OVERLAP_SLOP (0.5 cm) gets PHYS_OVERLAP_FIX (0.2) of it per step as extra speed apart, not warm started. Bounce after positions, along the line of centers at touch, with the speed that gives one bounce's energy. Plan A (bias instead of the push, old order) was dropped as a hack. Names: ParticleContact, particle_contact_find_spheres / _plane, particle_contacts_warm / _solve / _bounce.
- Integrator: semi-implicit Euler (velocity first, then position with the new velocity), not the book's order (2026-10-31). The book (ch 3, pdf 74 / book 51) drops 1/2 a t^2 as negligible and moves position with the old velocity, counting on damping < 1 to soak up the error. Under gravity that adds 1/2 g^2 dt^2 of energy per step, always the same sign: with damping 1 a 10 cm hop at restitution 0.85 never died out (37 of 80 balls still hopping at 60 s). Swapped order: all still by 10 s. Test: test_small_bounce_settles.
- Ball scene bounce: balls 0.6, walls 0.5 (was 0.9 / 0.85, looked rubbery and floaty) (2026-10-31).
- 3D balls drawn as real meshes (sphere mesh, per instance model matrix, depth buffer), not impostors. Chosen over impostors so rigid bodies (ch 9-11) reuse it (2026-10-31).
- Camera: free fly, perspective (2026-10-31). Click locks the mouse, click again releases (Esc also releases, browser rule). The camera only moves while locked: mouse look and keys (WASD, E/Q) do nothing when unlocked, so the slider panel can be used without drifting. W moves along the view direction (noclip). E up, Q down (world axis). Space stays respawn. ~5 m/s, Shift ~4x. Pitch clamped short of straight up/down, no roll. Start in front of the box, a bit above, looking at its center.
- 3D scene look: box 16 x 9 x 9 m. Solid floor plus 12 edge lines, no wall faces. One fixed angled light from above plus ambient, no shadows. Icosphere (~320 triangles), one mesh scaled per ball, all balls in one instanced draw (2026-10-31).
